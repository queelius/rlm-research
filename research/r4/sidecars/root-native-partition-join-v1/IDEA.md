# Native Python purchase join — design options, awaiting MAIN selection

2026-09-09. CPU-only source-reviewed proposal; no implementation, acquisition, service, GPU, or queue change. Historical partition outcomes informed this design. This is not a prospective registration of those outcomes. The brainstorming skill keeps implementation behind MAIN's selection.

## Recommended smallest informative comparison

24 new root endpoints: four fresh isomorphic worlds × three evidence states (direct original records; full co-located partial reports; full cross-partition partial reports) × two interfaces (no executable tools; native IPython available). One fresh paired sampling seed per world, balanced six-condition dispatch order. Deduplicate direct across partitions: it has no partition-dependent input. Four world clusters, not 24 independent replications.

Use the same released Qwen3-4B-Instruct-2507 base as both partition studies, with no research adapter. Do not inherit the restart task's low66c root/c32 child binding. The proposed tool contrast is initially native RLM/IPython availability, not a claim that Python computation alone caused any gain: record any subordinate model calls separately. If MAIN requires a Python-only causal contrast, prohibit child model calls using a separately CPU-qualified native depth/route restriction; do not silently patch or fake their responses.

Both interfaces receive the complete arm-specific evidence inline, with identical query, field definitions, customer domain, role wording and final contract. The tool interface additionally has byte-identical evidence files available through native Python. No-tools must not be file-only. Direct sees original record sentences; report arms see the complete unmerged three reports and their chunk identities, not original records as well. This deliberate mutually exclusive representation contrast differs from the historical pilot, where every parent saw originals plus reports. Record order has no temporal significance. Do not reveal whether a partition is engineered cross/co-located.

Use a common concise instruction to return only a sorted, distinct JSON customer-ID array. Python is optional; no intersection/group-by recipe, worked join, counting helper, supplied final answer, mandatory code use, or grammar on action turns. Keep the same native role text wherever possible; document native tool-schema/template changes as part of the availability package. A native tool call is not a final answer. Free manual finals can succeed; an accurate printed tool result without a final remains operationally unfinished.

## Worlds and report acquisition

Preserve the original scale: 12 customers, 48 purchase records, three balanced 16-record chunks, two queried products and two distractors; four answer cardinalities 3/5/7/9. Freeze new generator seeds before sampling; regenerate shuffled customer assignments, opaque record/customer identifiers, record order and product-symbol relabeling. Verify exact record conservation, equal chunk sizes, same global gold under both partitions, zero local queried-product conjunctions in cross, and recoverable local conjunctions in co-located. These are new instances of the exposed generator family, not a new task or broad generalization test.

Preferred acquisition: 24 fresh native extraction calls (three per eight report coordinates), using the existing full-triple extraction contract. Preserve raw outputs and all errors; no repair, retries, regeneration, or successful-subset selection. Both tool conditions share the same actual reports. Independently score exact extraction and report-implied answer versus dataset gold. A valid but wrong extraction is delivered unchanged; malformed/unavailable extraction remains explicitly marked and all planned endpoints remain inventoried. Do not promise complete reports before observing acquisition. The host reducer is an independently reported sufficiency/end-to-end baseline and is never shown to a root.

Cheaper alternative: losslessly serialize source triples into three supplied reports, with zero acquisition calls. This cleanly tests executable composition of complete facts, but must be labeled host-prepared evidence, not fresh model extraction or a full model pipeline. MAIN should select this explicitly if acquisition is not part of the immediate question.

## Metrics, bounds, and decisions

Primary: strict whole-native-final correctness on the planned denominator, accompanied by native-final availability, available-only accuracy and missing-final bounds. Returned malformed or capped final text is observed incorrect; no returned native final is NULL. Operational success counts bounded episodes that never return as unsuccessful without changing the native-final metric. No prose extraction, sorting, deduplication or host answer substitution.

Separately report report-consistent correctness; ID precision/recall on valid arrays; tool routing; actual file reading; actual across-chunk aggregation; printed result; result-to-final fidelity; Python errors; child calls; loops; cap/context exhaustion. Executed aggregation requires source-to-result data flow in recorded model-authored code and actual tool observations, not merely importing Python, loading a file, naming an intersection, or printing a literal. Audit code as text, not by rerunning generated code.

Compare tool-minus-no-tool within each evidence state, report-minus-direct within each tool condition, and cross-minus-co-located reports within each world. Successful tool-enabled cross joins with verified aggregation establish capability in this interface; manual success does not establish execution benefit. A report advantage is a representation effect, not proof of learned communication. If both direct and reports fail, do not diagnose cross-partition communication loss. If finals fail but executed results are correct, target stopping/final transfer rather than join training.

Physical cost counts 24 new extractions once plus all actual new root/child request attempts and returned-completion usage. Each standalone report endpoint also carries its own three acquisition calls: 48 hypothetical acquisition charges across 16 report endpoints, not 48 physical extractions. Keep rejected requests, unknown usage, billing unknowns, elapsed runtime and predecessor waiting separate. Provisionally four workers, 180-second root episodes, 2560 tokens/action, bounded native call/context budget, 1500-second inclusive work and 1650-second outer owner; exact limits require CPU native-prefix and lifecycle composition qualification before READY.

## Alternatives and reuse estimate

12 tool-enabled roots alone (four worlds × three evidence states) answer feasibility but cannot identify a tool-availability effect against historical different-interface outcomes. Recommended24 is the smallest screen retaining that contrast. A second predeclared seed doubles roots to48 and improves sampling precision, but still has only four world clusters; defer until a signal or ambiguity warrants it.

Reuse the original `root-partition-report-pilot-v1/pilot.py` generator topology/extraction contract and strict oracle; `root-partition-final-interface-v1` released-base service/native token authentication; `root-artifact-restart-v1` fresh runtime, file attestation, native trajectory/final capture, four-worker collector and bounded lifecycle. New pieces are a join task without TREC fields/helpers, base-native binding composition, no-tool path, fresh world/plan rendering, join scorer, and executed-aggregation audit. These seams prevent a safe filename-only port. Estimate roughly 45–75 minutes of bounded CPU preparation/qualification after selection, not a launch promise. Tests should cover native tool/no-tool bodies, a deterministic authored fixture exercising genuine Python observations and terminal capture, all world invariants, no repair/NULL behavior, and the actual owner→collector entry with service launch stub. No broad repository tests.
