# Fixed cp32 terminal-clamp paired audit

Approved scope: read-only CPU analysis of original cp32 held16×2 versus the queued `terminal-strip-disabled` arm. No model calls, learned parameters, input changes or polling service. Preserve the original returned-answer score and unchanged official scorer. The 32 trials are two repeats of 16 research-exposed contexts, not 32 independent units.

`analyze.py` reuses the exact sealed collector's native causal/availability classifier, while independently replaying the installed old/new parsers and comparing all returned native prompt/action-token arrays, sampling/model fields, tool arguments/programs and observations in episode order. Random provider/session IDs and wall timestamps are not identity requirements. Completion log-probability equality is recorded separately; no likelihood/RL claim is made. Exact model/adapter/checkpoint, schedule and prefix lineage comes from the reviewed 324-file source closure; a new output's binding must equal the completed comparator.

Only an available paired recovery with the complete same prompt/action/model/sampling/tool/observation path and an originally token-exact lost final is called `strict_clamp_only_recovery`. Same seed alone is insufficient. Different-length paths, errors, different tokens, altered prompts or different programs remain explicit. The analysis saves per-action token/prompt hashes and equality flags; full arrays/programs stay in authenticated source files, not duplicated in the summary. Genuine extra line feeds, punctuation changes and invalid/failed selectors retain separate raw categories; paired paths permit inspecting the same failures across arms.

Owner termination is required before reading the new result as terminal. An incomplete or failed owner is not zero accuracy: planned32 remains, available comparisons are explicit, and missing/unattempted coordinates remain in the paired list. Physical starts, returns, errors/start-only and observed token subtotals are reported separately. A missing optional science RESULT after owner failure does not imply a successful run. Setup/provider failures are not ordinary incorrect answers.

Preparation uses one fixture based on an actual archived episode: token mutation, prompt mutation and call removal must invalidate the corresponding identity condition, and the actual collector seam must recompute its saved initial-prefix/causal/score evidence. `prepare.py` also runs the old completed full32 through the concrete stage reader before sealing, without any new rollout.

Commands (from this directory, native Python, CUDA hidden):

```sh
CUDA_VISIBLE_DEVICES='' PYTHONDONTWRITEBYTECODE=1 /project/alex_phd/envs/prime-rl-5990b1b/bin/python analyze.py verify
CUDA_VISIBLE_DEVICES='' PYTHONDONTWRITEBYTECODE=1 /project/alex_phd/envs/prime-rl-5990b1b/bin/python analyze.py check --output completion-check-001.json
```

The check is **one shot**, with no sleep or retry. A pending check explicitly says PENDING. Subsequent MAIN-triggered terminal checks use a new output filename; existing results are never overwritten. The new-model screen is a separate analysis, including runtime loop/idle boundaries, not a model ranking.
