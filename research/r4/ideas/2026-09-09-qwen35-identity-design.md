Status: CPU-feasible design proposal, not a launch READY. No model weights were loaded, no GPU or model request was made, and no new package/data/model was acquired. Neither uses original857a, old c32de, or any research SFT adapter. These are **post-trained/instruction checkpoints**, not pretrained base models; “base” here means no research adapter.

Each model gets 12 contexts × two fresh sampling seeds × three output representations = 72 calls, 144 total. Proposed master 981302001, seeds 981302011/981302021, subject to the usual bounded named-plan collision check before freeze. All three use exact 64-position grammar: plain label strings; tag-then-label objects with actual matching source IDs; equally shaped objects with constant `p0000`. All IDs/text/order/definitions/labels/system/tools remain identical within a context; only the output instruction and schema differ. This tests *constrained output representation*, not natural-output instruction following. There is no sparse cadence intervention in this follow-up.

Retain the source body’s legitimate generic system and tool definitions for comparability with existing component work. Grammar prevents tool output in all arms. Position is the primary alignment; matching tags are independently validated, never used for offline repair/reordering. Constant objects must remain constant. Duplicate keys, missing records, extra records, wrong tag values, noncanonical labels or malformed output are observed strict failures, not repaired arrays. Report key-order adherence separately from key-set/tag/label validity; expected wire grammar forces tag then label, but lexical order is not secretly an alternative alignment rule.

Rotate the six possible three-arm orders across the 24 context/seed triples, identically for both models; four work-conserving workers, one request per coordinate, no retries/replacements. Record actual dispatch order. Sequential model order is fixed and a service-stage confound, not randomized model timing.

## Primary question, outcomes and decision

Primary: matching-minus-constant strict correct assignments within each context/seed, separately by dataset and model. Does the effect retain sign and material magnitude on Qwen3.5? Secondary: matching-minus-plain; model difference within each representation; first/last 16 position accuracy; valid 64-arrays; whole-array exactness; class-count L1; actual input/output/reasoning/cache tokens, missing usage, latency and service wall time. Report four context-level means per dataset with nested seeds; 1,536 label occurrences per model/representation are not independent samples.

Keep completed-invalid outputs as score 0 and alignment unavailable; infrastructure, timeout and unrun as null with planned denominators and bounds. Do not pool task scores to hide a task interaction. Public-source memorization and all prior local exposure remain unknown/confounded; there is no new data generalization claim, no SFT-specific attribution and no end-to-end RLM gain.

Prospective screen thresholds, not significance tests: promote cross-generation replication if Qwen3.5 matching beats constant by at least 10 percentage points in two tasks and has positive context-mean differences in at least three of four contexts in those tasks. Revise toward “Qwen3-specific failure/compensation” if Qwen3.5 plain and constant reach at least 95% and matching is within 2 points. If matching falls within ±2 points with non-ceiling baselines on both models, retire this narrow source-matching mechanism under these conditions; inspect task interactions rather than add training. Any substantial incomplete coverage defers these decisions. A stronger/faster candidate means better strict accuracy at comparable or lower measured component wall/output cost, not model-card claims or merely fewer tokenizer tokens. This tiny sequential run cannot establish hardware-independent throughput.

## Model, template and reasoning facts

The cached Qwen3.5 model is Apache-2.0, acquired 2026-09-02T19:00:49Z, exact HF revision above. Its config names `Qwen3_5ForConditionalGeneration`: 32 layers, every fourth full attention, the other layers Gated DeltaNet; hidden size 2560. This specific 4B checkpoint is **dense**, despite the family-wide model-card highlight mentioning MoE. It also contains a vision encoder and MTP weights. A header-only safetensors inspection counts 4,205,751,296 other/text stored elements, 333,514,240 vision and 120,599,552 MTP; 3,840 F32 elements and 4,659,861,248 BF16 elements. These are stored tensor elements, not a measured active-parameter or memory claim. Use language-model-only and no MTP. Model-card benchmarks do not answer this exposed classification question. [Pinned official model card](https://huggingface.co/Qwen/Qwen3.5-4B/blob/851bf6e806efd8d0a36b00ddf55e13ccb7b8cd0a/README.md).

Set `chat_template_kwargs.enable_thinking=false` explicitly for every call. Qwen3.5 defaults to thinking; its actual cached template appends `<|im_start|>assistant\n<think>\n\n</think>\n\n` when disabled. Qwen3 Instruct appends only `<|im_start|>assistant\n`. Thus common message text does **not** imply identical physical prefixes/token IDs. Save each model’s actual template, typed tool serialization and complete provider prompt IDs, and compare against its own frozen CPU render. The inherited `typed_prompt_ids` helper currently omits template kwargs: the new private helper must pass them; calling it unchanged would incorrectly qualify Qwen3.5 thinking mode.

Installed vLLM 0.28.0 explicitly registers the Qwen3.5 architecture; its qwen3 parser honors `enable_thinking=false`. Use reasoning parser qwen3 on Qwen3.5, no parser on non-thinking Qwen3. Exact schema applies to answer output; empty thinking is supplied by template, not sampled or silently stripped. Inspect actual returned reasoning and output IDs and fail the protocol check if unexpected reasoning bypasses constraints. Do not enable grammar inside free reasoning or compare reasoning-enabled against disabled models. Official vLLM supports reasoning plus structured outputs, but parser/configuration matter. [vLLM structured-output documentation](https://docs.vllm.ai/en/v0.28.0/features/structured_outputs/).

CPU proof used installed Transformers 5.6.2, xgrammar 0.2.1 and vLLM 0.28.0. All 36 distinct context/format bodies per tokenizer validate as typed requests and admit a legal synthetic exact-schema answer. Maximum prompt+3072 is **7,766 Qwen3 / 7,894 Qwen3.5**, both below 8,192, with complete source text. Seeds do not affect rendering. This is positive grammar/tokenizer feasibility, not GPU model execution; final qualification still needs negative cardinality/tag fixtures and exact provider IDs at launch. The CPU probe did not claim hard maximum length for every possible answer.

## Minimal serving adaptation and resource cap

Reuse the pinned component collector, raw HTTP capture, strict scorer and qualified ownership/release lifecycle. Existing `leaf-role-routing-v1/source/serve.py` hardcodes Qwen3 and adapter loading; it cannot honestly serve this comparison unchanged. A small new private base-service adapter must set the model path, omit all LoRA loading, write a base-checkpoint endpoint descriptor with no adapter, and preserve the established process-identity/port checks and finally release. Never fake a base model as a LoRA alias. Reuse original launcher environment/MIG UUID/LD paths; no CUDA=0, new container or environment.

Proposed common inference settings: BF16, tensor/data parallel 1, max length8192, max sequences4, eager mode, prefix cache disabled, generation_config=`vllm`, no FP32 LM-head/router patch, no speculation. Explicit common request sampling T0.5, top_p1, top_k−1, min_p0, repetition_penalty1, presence/frequency penalties0, max output3072. These avoid model-specific generation defaults and make this a new common runtime comparison, not a pooled historical speed test. Retain/log tool definitions; parser can be hermes for Qwen3 and qwen3_coder for Qwen3.5, with no auto-tool generation under exact schema. Qwen3.5 alone sets language_model_only=true and mamba_cache_mode=align. The installed model explicitly rejects mamba `all`; GDN source has an Ampere-compatible Triton path, but an A100 run remains unqualified. Prime config validation accepted these pass-through settings CPU-only. Official recipe identifies language-model-only and notes experimental hybrid prefix caching; we avoid the latter. [Official vLLM recipe](https://docs.vllm.ai/projects/recipes/en/latest/Qwen/Qwen3.5.html).

Per model: load/start cap300s, collect cap900s, per request120s, owned cleanup120s. Whole work cap2400s, owned inclusive2640s, parent2670s; no borrowing/retries beyond that absolute cap. Expected roughly20–35 minutes total including two loads, explicitly uncertain on new kernels/eager runtime. Stop with a preserved startup failure if Qwen3.5 fails; do not install or switch backends automatically. Release the first model completely before the second starts. Bound checkpoint is every call plus service/stage markers; there is no training or checkpoint selection.

Alternative if private base-service seam is not small: prepare only the Qwen3.5 72-call component stage and label comparison to existing adapter results non-equivalent; do not spend effort generalizing the scheduler. The preferred 144-call design supplies the proper fresh no-adapter Qwen3 baseline.
