# Preserve child evidence before asking the root to count

Recommendation: a16-episode whole-RLM comparison of unchanged typed maps versus the same maps plus an automatic cumulative, query-independent label summary. Keep root/child weights, original prompts, helper/API, child grammar and sampling fixed. Do not start with a new count API or more interface SFT. This is a proposal only: no implementation, runtime patch, GPU call or accepted-source edit occurred.

## What the observed failure actually establishes

The named validation4 case contains32 unique, source-bound child labels on the final root's physical ancestral branch. Their histogram includes three `numeric value` labels, yet the root returns `Answer: 6`. Its eight sampled Python actions each overwrite `labels` and print one four-record map. This isolates a useful failure example: the necessary classification evidence reached the root, but the final answer did not preserve its aggregate. It does not establish how often this failure occurs, that classification is generally solved, or that every wrong answer is an accumulation failure. The case was selected post hoc and must not become a fresh evaluation observation.

## Three feasible options

| Option | What changes | What it can identify | Main limitation |
|---|---|---|---|
| Accumulator example | Replace the public mini-example with persistent `all_labels.update(...)` and an executable count | Whether a small procedure-teaching intervention repairs observed behavior | Root must choose/use the example; changes prompt/action distribution and does not separate instruction uptake from state preservation |
| Automatic accumulation ledger — preferred | Preserve raw child answers; append a supervisor-derived union histogram and coverage after root tool execution | Whether reliable persistence/arithmetic from actual child evidence improves a freely acting root's final fidelity | Harness performs the accumulation; gains do not show the root learned it, and additional observations can change later planning |
| Authored terminal-prefix diagnostic | Supply a fixed set of returned maps, with/without its summary, then sample a root continuation | Whether the model can read and use a summary given identical evidence | A component/replay experiment, not evidence of autonomous collection, helper uptake or whole-RLM success |

The middle option avoids another unfamiliar API and preserves the already-successful `await rlm(request_for(batch))` / `strict_map(child.answer, ids)` behavior. A query/count tool is more invasive: the model must learn to call it, and a query-aware operator can quietly take over filtering and aggregation. Do not build that broader system yet.

## Ledger semantics: evidence, not an answer oracle

The ledger is per root invocation and context, keyed by source ID and the exact fixed six-label classification contract. It admits only successfully returned depth1 child results whose request round-trips the public source-bound batch contract and whose raw answer passes duplicate/missing/unknown-ID and canonical-label checks. It never reads host gold, reward, answer fields, or semantic annotations; does not infer labels for unqueried records; and does not replace malformed or failed results. Ordinary unmatched/custom children remain ordinary and are excluded, with an explicit reason.

Accumulate each unique ID once. Repeated equal labels are idempotent, not extra records. Conflicting labels make that ID permanently unresolved for the episode; do not choose the first/last/majority or silently resolve it using gold. A summary reports unique seen, resolved, unresolved/conflicting, and unqueried counts, plus all six canonical-label counts over resolved IDs. No target category is singled out and no `Answer`, task-correctness flag or target-specific count is supplied. The root still decides when to stop and which count to report. For the global tasks the histogram necessarily makes arithmetic easy; that is the declared intervention, not a discovery that the root independently learned accumulation.

Illustrative automatically generated observation, appended after the original root tool output:

```text
[Harness label ledger — counts of actual source-bound child predictions, not verified labels]
Unique source IDs seen: 8 / 32. Resolved: 8. Conflicting: 0. Unqueried: 24.
Counts over resolved unique IDs:
human being=1; location=2; abbreviation=0; entity=2;
description and abstract concept=1; numeric value=2.
This is partial evidence, not a final task answer. Original child maps are unchanged.
```

At full coverage, print `Unqueried: 0`, not “task solved.” If a child misclassifies a question, the ledger faithfully counts the wrong classification. Failed/malformed child events are retained separately; do not add their requested IDs to resolved coverage. No per-user table or natural-language query parser in this first global-only test. A future user-filter ledger would require separately declaring how metadata joins/subset scopes are chosen.

## Cheap fallback and brief literature context

If the narrow runtime hook fails, a separately labeled16-continuation diagnostic can use the same four contexts/two seeds and two authored prefixes containing fixed non-gold child maps with/without their deterministic summary. Sample only the ensuing root continuation. Freeze all eligible source branches or a rule-selected set before outputs; never cherry-pick a successful/wrong child map based on future outcomes. Replayed child observations cost zero new child calls and are not actual fresh child executions. The supplied prefix/tool actions have no behavior likelihood and cannot be training data labeled as sampled root actions. A positive result only establishes readout ability given supplied evidence, not whole-RLM uptake or an operational ledger gain.

The related principle is established, but not a guarantee here. PAL separates language-driven decomposition from deterministic execution to avoid arithmetic/logical mistakes; its model-generated programs differ from the proposed harness-authored union operation. [PAL, arXiv:2211.10435v2](https://arxiv.org/abs/2211.10435v2). LOTUS exposes semantic operations such as filtering, grouping and aggregation as composable data operators; its accuracy guarantees are relative to a declared reference algorithm, not proof that child labels are ground truth. The proposed ledger deliberately stops short of a semantic query engine. [Semantic Operators, arXiv:2407.11418v3](https://arxiv.org/abs/2407.11418v3). Only these primary abstracts were checked for this short design; no cloning, package installation or broad literature project was undertaken.
